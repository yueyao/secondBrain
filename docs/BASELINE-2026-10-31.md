## 4. 发现的问题（重要）

### 4.1 所有新节点共享全部 claims（结构性重复）

渲染模板把 draft 的**全部 claims** 写进每个新节点的「核心观点」，结果是：

```
5 个节点 × 11 条 claims = 55 条内容，实际只有 11 条是独立的
```

这会让节点之间高度重复，与 secondBrain 的"节点 = 一个明确判断"原则冲突。**这是当前 schema 的缺陷**：`DraftProposal.nodes` 没有"这个节点对应哪些 claims"的映射。

**建议**：节点结构增加 `claimIndexes`（或 `claims` 数组），提示词要求模型为每个节点标注它支撑的 claim；渲染时只写对应 claims。这是 P6 的第一优先级。

### 4.2 节点粒度偏抽象

「允许结构性失衡」「目标即约束条件」这类命名接近"观点/原则"，容易在跨文章时产生近义重复；而当前检索是**精确名/别名匹配**，无法识别「允许结构性失衡」≈「接受阶段性不完美」。

**建议**：节点命名规范（名词短语优先）+ 同义判定（后续可加 embedding 检索或别名词表维护）。

### 4.3 无 patch 分支被验证

本次是空库，全部 `new`；对真实 wiki（4,532 个节点）的 patch 行为还没验证——需要第二批基线（带既有节点）。

## 5. 成本外推（粗估）

| 场景 | 估算 |
|---|---|
| 单篇（~7KB，本样本） | $0.0025 |
| 单篇（60KB 长文，上限） | ~$0.02–0.03 |
| 现有 backlog 2,000 篇（按平均 0.005） | **≈ $10** |
| 全库重跑一遍（13k raw，按 0.005） | ≈ $65 |

> 结论：**flash 的成本对这个项目几乎可忽略**；主要成本是人的审核时间，不是模型费。这也反过来支持"先全用 flash 跑通"的策略。

## 7. 结论与下一步

**结论**：flash 能产出**可用**的 claims（来源 100% 可追溯、判断密度 0.5、推断仅 9%），成本可忽略；主要问题在**节点与 claim 的对应关系**，不在模型。

**下一步优先级**：

1. **修 schema**：节点绑定 claims（P6.1）；
2. 带既有节点跑 5–10 篇，验证 patch 分支与命名冲突；
3. 批量 30 篇统计密度/重复率，形成可对比的基线表；
4. 用 golden set 对比 flash vs v4-pro（质量/成本曲线）。
