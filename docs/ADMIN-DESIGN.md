# 管理后台信息架构重构（设计稿）

> 状态：待确认（2026-11-03）。目标：从"一个页面堆信息"改成"按任务分层"。

## 1. 现状诊断

当前 `/admin` 把三类东西混在一页：

| 混在一起的内容 | 问题 |
|---|---|
| 运行监控（worker 状态、今日进度、ETA） | 每次打开都要看，但不该和运维操作同级 |
| 运维操作（扫描、暂停/继续） | 与统计混排，误点风险；缺少"立即执行一次""同步""备份状态" |
| 内容统计（状态分布、最近事件） | 数字不可点，无法下钻；文章库要另开页 |

其他不便：

1. **主任务（审核草稿）没有独立入口**：首页只列前几篇，草稿多了要在首页滚动；
2. **文章库筛选弱**：只有状态下拉 + 关键词，没有来源/日期/triage 分组，不能看"今天新进来的"；
3. **状态是平铺的 18 个值**：用户真正关心的是 5 个分组（待处理/待审/已入库/已延后/异常）；
4. **数字不可点击**：看到"待审 15"不能直接进列表；
5. **运维动作无结果反馈**：点了暂停只改文件，看不到"上次同步/备份是什么时候、成功没有"；
6. **导航只有 5 个平级链接**：没有层级，也没有"当前在哪里"的提示。

## 2. 设计原则

1. **任务优先**：默认落地页回答"我现在该做什么"（审核），而不是"系统状态如何"。
2. **三层下钻**：工作台（概览）→ 列表（可筛选）→ 详情（单条 + 操作）。
3. **内容与运维分离**：`/operations` 只放系统控制；内容统计回到工作台。
4. **数字即入口**：每个 KPI/状态计数都可点击，跳到带筛选的列表。
5. **状态分组**：18 个内部状态 → 用户可见 5 组；组内再展开英文（可选）。
6. **实时状态常驻但不抢戏**：全局顶栏一个 worker 状态灯（运行/暂停/离线），详细控制在运维页。
7. **动作可预期**：所有写操作有明确后果文案 + 结果回显（最近一次执行时间/结果）。
8. **URL 可分享**：筛选条件全部进 query string。

## 3. 新的信息架构

```
全局顶栏（所有页面）
├─ 左：secondBrain  ·  工作台 / 文章库 / 审核 / 运维 / 用量
├─ 右：worker 状态灯（● 运行中 / ⏸ 已暂停 / ○ 离线）+ 待审计数 badge
└─ 内容区

/               工作台      ← 默认落地：今天该做什么
/articles       文章库      ← 全部 4,408 篇，按 5 组 tab + 筛选
/articles/<path> 文章详情   ← 单篇：内容 + 右侧操作栏 + 时间线
/review         审核中心    ← 草稿列表（待审/已批准/已驳回）+ 键盘审阅
/operations     运维中心    ← worker/同步/备份/日志；原 /admin 拆出
/usage          用量        ← 成本与 tokens（保留）
```

### 3.1 工作台 `/`

| 区块 | 内容 |
|---|---|
| 今日概览 | 今日起草 / 待审 / 今日入库 / 剩余队列 + ETA（每个数字可点） |
| 待审队列 | 前 5 篇草稿，一键进入审阅；「查看全部」→ `/review` |
| 异常提醒 | failed / blocked / rolled_back / 超 24h 未处理，最多 5 条 |
| 进度条 | 队列消化进度（已处理 / 总量） |
| 最近活动 | 最近 10 条事件（审核、入库、失败） |

### 3.2 文章库 `/articles`

- **Tabs（5 组）**：全部 / 待处理 / 待审核 / 已入库 / 已延后 / 异常（= 状态映射）
- **筛选栏**：来源（cubox/dedao/podcast/…）、日期范围（今天/7 天/30 天/全部）、triage（高/中/低）、关键词
- **表格**：标题、来源、状态（中文 badge）、判断句数、字数、更新时间；支持按列排序
- **行内操作**：查看 / 重新起草 / 延后
- **批量**：勾选后「批量延后」「批量重新排队」（P8.5）
- **URL 示例**：`/articles?group=queued&source=podcast&days=7&sort=judgments`

### 3.3 文章详情 `/articles/<path>`

| 区域 | 内容 |
|---|---|
| 左主列 | 状态与 triage → 草稿（claims / 节点 / claimIndexes / findings）→ 提交记录 |
| 右操作栏 | 去审阅 / 重新起草 / 延后 / 复制路径 / 打开原文（后续） |
| 时间线 | 该文章的 ingest / triage / draft / review / commit 事件 |

### 3.4 审核中心 `/review`

- 左列表：待审草稿（可按 tier、来源筛选），键盘 `j/k` 切换、`a` 接受、`r` 驳回；
- 右预览：现有 review 视图（claims、节点、findings、通过/驳回）；
- 顶部：待审计数与「全部接受」不提供（必须逐篇，避免误操作）。

### 3.5 运维中心 `/operations`

| 分区 | 控件 / 信息 |
|---|---|
| worker | 状态灯、当前任务、暂停/继续、**立即执行一轮**、上一轮结果 |
| 同步 | 上次 sync 时间与结果、**立即同步**（git pull） |
| 备份 | 上次备份时间/文件大小/integrity、**立即备份** |
| 危险区 | 暂停全部处理（同 worker 暂停）、清空暂停标记 |
| 日志 | worker 最近 20 行（读 journal 或状态文件） |
| 环境 | 模式、dataDir、vaultRoot、版本/commit |

每个按钮都显示「上次执行：时间 · 结果」。

### 3.6 状态分组映射（用户可见）

| 组 | 内部状态 |
|---|---|
| 待处理 | queued, ingested, triaged |
| 待审核 | draft_ready, in_review |
| 已入库 | committed |
| 已延后 | deferred, rejected |
| 异常 | failed, blocked, rolled_back, expired, abandoned, quarantined |

内部 18 个状态仍在详情/筛选高级项里可见（中文）。

## 4. 技术分层

```
视图层（apps/server/views）
├─ layout：顶栏 + nav + flash 消息
├─ 组件：statCard / statusBadge / filterBar / table / timeline / actionForm
└─ 页面：workbench / articles / article detail / review / operations / usage

视图模型层（apps/app/queries）
├─ workbenchVM(ctx)：今日 KPI、待审前 5、异常、事件
├─ articleListVM(ctx, filters)：分页 + 分组 + 排序
├─ articleDetailVM(ctx, path)：内容 + 操作可用性
├─ reviewQueueVM(ctx)：草稿列表 + 当前草稿
└─ operationsVM(ctx, fs)：worker/暂停/同步/备份状态（文件读取留在 server 层）

动作层（server actions）
├─ POST /actions/worker/pause|resume|run-once
├─ POST /actions/sync-now
├─ POST /actions/backup-now
└─ POST /actions/articles/:path/requeue|defer（P8.5）
```

**分层要点**：页面只读"视图模型"，不直接拼多个 summary；文件/系统信息只在 server 层读取后传入，保持 app 层纯函数。

## 5. 实施顺序（建议）

| 阶段 | 内容 | 价值 |
|---|---|---|
| P8.1 | 拆分 `/admin` → `/operations`；全局顶栏 + worker 状态灯；工作台吸收统计 | 立刻消除混排 |
| P8.2 | 文章库 5 组 tabs + 筛选栏 + 排序 + 数字下钻 | 日常最常用 |
| P8.3 | 审核中心独立页 + 键盘操作 | 提升审核效率 |
| P8.4 | 运维动作（立即跑一轮 / 立即同步 / 立即备份 + 结果回显） | 减少登录服务器 |
| P8.5 | 批量操作、异常中心、时间线 | 规模化后需要 |
